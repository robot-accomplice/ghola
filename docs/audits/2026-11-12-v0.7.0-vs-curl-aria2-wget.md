# Audit: ghola v0.7.0 against curl, aria2 and wget

Date: 2026-11-12. Commit: `main` at `cd2c6a7` (same tree as tag `v0.7.0`).

## Verdict

ghola is not safe to use as a curl, wget or aria2 replacement today.

1. The `--serve` bridge lets any web page send requests from the user's machine and write files to paths the page chooses. `scope` starts this bridge by itself.
2. Segmented downloads and resume can write a corrupt file and exit 0. curl and aria2 refuse the same input.
3. ghola sends credentials to a different host after a redirect. curl does not.
4. The body on stdout is not byte-exact. Every pipe through ghola changes the data.

The happy paths work: plain downloads, resume, segmented downloads, rate limits on files, TLS checks and retries. The failures are all in the edge cases. A forensic tool is judged on its edge cases.

## Method

1. A local Go test server served deterministic content and hostile cases: a server that ignores Range, a server that sends a wrong `Content-Range`, a truncated body, a hang, redirect chains, a cross-host redirect, gzip, `Content-Disposition` path traversal, flaky 503s and self-signed TLS.
2. The same scenarios ran on 4 tools: ghola v0.7.0 (built from `main`), curl 8.18.0 (mingw64), aria2 1.37.0 and GNU Wget2 2.2.1. Wget 1.21.4 was not tested: its winget package failed the hash check, so Wget2 stands in for wget.
3. Each run recorded exit code, time, stdout hash, stderr and the files written. The server logged every request.
4. Code reading confirmed the cause of each defect.

Platform: Windows 11, loopback only. Not tested: Linux and macOS, real network latency, proxies, HTTP/3, Ctrl-C handling, and impersonation fingerprints against a live fingerprinting service.

## Findings

Severity: **Critical** means data loss, corruption with exit 0, or a remote attack path. **High** means wrong results or a crash in normal use. **Medium** means behaviour that differs from what curl users expect, or wasted resources. **Gap** means a missing feature.

### Critical

**C1. The `--serve` bridge accepts commands from any web page.**
- The bridge on `127.0.0.1:18789` has no authentication. It does not check `Origin` or `Host`, and it accepts any `Content-Type`.
- A browser sends a `text/plain` POST without a CORS preflight. A web page can therefore make the bridge send any request (SSRF into the local network) with the user's IP address.
- The JSON field `cookie_jar` is a file path. The bridge writes the jar to that path. `proxy_file` reads a file from a path the caller chooses.
- The bridge accepts a foreign `Host` header, so DNS rebinding can also read the responses.
- `scope` starts `ghola --serve` by itself (`scope/src/http/ghola.rs:106`) and leaves it running.
- Repro: `curl -X POST -H "Content-Type: text/plain" -H "Origin: http://evil.example" -H "Host: evil.example:18789" --data '{"url":"http://127.0.0.1:18080/cookie/set","cookie_jar":"C:/.../planted-by-webpage.json"}' http://127.0.0.1:18789/`. Result: 200, and the file exists.
- Fix: require a random token (written to a 0600 file that `scope` reads). Reject requests whose `Host` is not `127.0.0.1:18789`. Require `Content-Type: application/json`. Remove `cookie_jar` and `proxy_file` from the bridge, or limit them to one directory.

**C2. A segmented download (`-n N -o file`) writes a corrupt file and exits 0 when the server ignores Range.**
- The server sends `Accept-Ranges: bytes` but answers each range request with 200 and the full body.
- ghola wrote 14,680,064 bytes for an 8,388,608-byte resource, with exit 0. aria2 detected the problem and wrote the correct file.
- Cause: the segment writer does not check for status 206 or for a `Content-Range` that matches the requested range.

**C3. Resume (`-C -`) corrupts the partial file.**
- When the server sends 206 with a wrong `Content-Range` start, ghola appends the body and exits 0. The result is 1,355,776 bytes instead of 1,048,576. curl refuses with exit 33.
- When the server ignores Range and sends 200, ghola appends the full body first and only then reports "server ignored resume Range". The user's partial file is destroyed. curl and aria2 leave the partial file unchanged.
- Wget2 also corrupts the file in both cases. ghola is equal to Wget2 here and worse than curl and aria2.

### High

**H1. Credentials go to a different host after a redirect.**
- `ghola -L -u alice:s3cret` sent `Authorization: Basic …` to `localhost` after a redirect from `127.0.0.1`. A custom `-H "Authorization: Bearer tok"` also followed the redirect.
- curl drops both, unless the user gives `--location-trusted`. Wget2 also leaks Basic auth.

**H2. The body on stdout is not byte-exact.**
- `internal/output/output.go:82` prints `bytes.Trim(body, "\n")` plus `"\n"`. Every leading and trailing newline is removed, and one newline is added.
- A 1,024-byte binary file arrived as 1,025 bytes. A gzip-decoded text body lost its last newline.
- `-v`, `-i`, ghost-signature and profile lines also go to stdout and mix with the body. curl writes `-v` to stderr.

**H3. `--timeout` does not apply to `-o` downloads.**
- The deadline is set only in `FetchURL` (`internal/client/client.go:210`). The streaming download path never gets it.
- `ghola --timeout 2000 -o f http://…/hang` ran until the test harness killed it after 60 s. Without `-o`, it stopped at 2 s.

**H4. `-n N` repeats requests and hides failures.**
- `-n 3 -d once` sent 3 POSTs. Repeating a non-idempotent request is a side effect the user did not ask for.
- `-n 3` against a refused port printed nothing and exited 0. `RunConcurrent` drops the errors, and `execute` always returns `NoError`.

**H5. `-r -1` crashes with a nil-pointer panic.**
- With a negative retry count, `FetchURL` returns a nil response and a nil error. `ProcessResponse` (`internal/output/output.go:25`) then dereferences the nil response.

**H6. Exceeding the redirect limit exits 0.**
- `ghola -L` on a 60-hop chain stopped at the limit, printed the 3xx body and exited 0. curl exits 47, and aria2 exits 23.

**H7. `-f -o file` still writes the error body to the file.**
- The README says `-f` suppresses body output. With `-o`, a 404 body was written to the file. curl `-f -o` writes no file.

**H8. `-u` credentials are not sent on a download to a file (added 2026-11-15).**
- `ghola -u alice:s3cret -o f <url>` gets 401. The server log shows that no request (2 HEAD, 2 GET) carries `Authorization`. Without `-o`, the same command works.
- curl, Wget2 and aria2 send the credentials and write the file.
- Cause: only `internal/client/client.go` (`FetchURL`) adds the Basic header. The streaming download path builds its own request.
- The audit did not find this: its Basic-auth case wrote to stdout. The parity harness found it (scenario `basic_auth`) when the scenarios that do not test stdout moved to file output.

### Medium

**M1. Every request has `Content-Type: application/json` by default.**
- This includes GET requests and `--impersonate chrome`. A real Chrome never sends a `Content-Type` on a GET navigation, so the default breaks the browser fingerprint that impersonation exists to create.
- `-d "a=1&b=2"` and `--data-urlencode` send form data labelled as JSON. curl uses `application/x-www-form-urlencoded`.
- Any `-H` replaces the whole default header list, so the default disappears without warning.

**M2. Output to stdout buffers the whole body.**
- The peak working set was 525 MB for a 256 MB body (the body plus a copy for `Trim`). curl streams. A multi-GB body on stdout runs out of memory.
- The `-o` path streams and finished a 256 MB download correctly. Its peak memory was not measured; the measuring harness failed on that path.

**M3. `--limit-rate` has no effect on stdout.** 256 KiB at `64k` took 0.10 s on stdout and 4.25 s with `-o`.

**M4. The progress meter is noisy and wrong.**
- It prints when stderr is not a terminal, so logs fill with progress lines.
- **Correction (2026-11-15):** this report first said "curl prints a meter only to a terminal". That is wrong. The parity harness (`test/parity`, scenario `progress_not_tty`) shows that curl 8.18.0 writes its full progress table to a stderr that is a file. Wget2 and aria2 do not. The audit check looked only for a percentage, and curl's table has no "%" after its numbers, so the check could not find curl's meter. The finding stays: a log must not fill with progress lines. But here ghola is equal to curl, not worse.
- With `--compressed` it showed "5456.1% 3601/66 bytes". With retries it showed "340.0% 17/5 bytes". The total comes from the compressed length, or from the first (503) response.

**M5. Each `-o` download sends a HEAD request first.** This doubles the request count. Some servers answer HEAD differently from GET, or do not allow it. curl, Wget2 and aria2 do not need it.

**M6. Exit codes carry little information.** DNS failure, refused connection, timeout and TLS failure all exit 2. Write failures and HTTP errors on `-o` all exit 4. curl gives 6, 7, 28, 60, 23 and 22, so scripts can react to each cause.

**M7. Weak input checks.**
- `--timeout -5` and `-n 0` are accepted.
- A header without a colon (`-H NoColonHere`) is dropped without a message.
- `-H "User-Agent:"` sends `User-Agent: fasthttp`, which exposes the HTTP library. curl removes the header.

**M8. Proxy environment variables are ignored.** `HTTP_PROXY` had no effect. curl and Wget2 use it.

**M9. URL handling.** Extra URLs on the command line are ignored without a message. A URL without a scheme (`127.0.0.1:18080/x`) fails. curl uses `http://` by default.

### Gaps compared with the reference tools

| Missing in ghola | Reference |
|---|---|
| `-I` (HEAD with headers), `-w/--write-out` | curl |
| `--resolve`, `--connect-to`, `--netrc` | curl |
| TLS version and cipher flags, HTTP/2 control | curl |
| Several URLs, URL globbing | curl |
| Input file of URLs, metalink, BitTorrent | aria2 |
| Recursive download and mirroring | Wget2 |
| `If-Range`/ETag check on resume | none of the tested tools (all 4 mixed old and new content) |

## What ghola does well

- TLS verification is on by default in both backends. `--cacert` and `-k` work.
- A truncated body gives a non-zero exit, like curl.
- ghola rejects CRLF injection in `-H`. curl sends the injected header.
- `Content-Disposition: filename="../../evil.txt"` is reduced to `evil.txt`, like curl and Wget2.
- Resume, segmented download, fallback when the server has no Range support, and chunked bodies all give correct files when the server behaves.
- `--limit-rate` on `-o` is accurate (4.25 s for the 4 s target).
- `--retry-http` retries 503 with backoff. 303 and 307 redirects keep the correct method and body.
- A 256 MB `-o` download, with and without `-n 4`, finished with the correct size.

## Notes on the reference tools

These are defects in the reference tools on Windows, not in ghola:
- Wget2 converts LF to CRLF on stdout (1,024 bytes became 1,028).
- Wget2 exits 0 when `-T 2` expires on a hung server, and after a 60-hop redirect chain.

## Fix order

1. C1: the bridge. It is an attack path on every machine that runs `scope`.
2. C2 and C3: check status 206 and `Content-Range` before writing any byte. Never change the existing partial file until the response is checked.
3. H1: drop `Authorization` and `Cookie` headers on a cross-host redirect.
4. H2 and M2: stream the body to stdout unchanged; send `-v`, `-i` and other metadata to stderr.
5. H3 to H7: timeout on streams, `-n` semantics and exit code, the panic, the redirect-limit exit code, and `-f -o`.
6. Medium items, then the gaps. Decide for each gap if ghola needs it: ghola is a fetcher, not a mirror tool.

Each fix needs a test that reproduces the case from this audit first.
